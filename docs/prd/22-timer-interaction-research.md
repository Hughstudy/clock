## 1. 先重新定义要解决的问题

**本轮判断：优先研究“在原段内重新安排剩余时间”，再研究“结束与下一段合并操作”。** 用户最初提出把结束与时间放进同一个操作框，这是可能的手段。更底层的目标是：工作或休息的安排临时变了，能够就地改时间，同时保留已经发生的过程，不必先学会应用内部的准备、结束和切换流程。

已知需求来自本轮对话：用户认为专注与休息切换点击多，选时间的入口距离远；随后明确优先关注每一段临时改时间，提前结束有时是为了继续做事、重新安排计时。这是本产品负责人的具体使用需要，不能据此推断全部用户的频率。用户要求以调研支撑判断，不继续用偏好问题代替研究。

上一版建议集中在“结束专注 → 选择休息 → 开始休息”，默认了结束之后主要是休息。这只覆盖了部分需要。若用户仍在做同一件事，只想再给自己10分钟，让她结束原段、再开一段，会增加操作，还把连续投入切成多条记录。

需要分别解决四种意图：

| 用户意图 | 应发生什么 | 不应被迫发生什么 |
| --- | --- | --- |
| 尚未开始，今天只做10分钟 | 选择本次时长，明确开始 | 修改长期默认值、先创建一段记录 |
| 已做8分钟，决定从现在再做10分钟 | 调整原段之后的时间，保留已投入8分钟 | 结束重开、丢掉原段想法、重复算参与 |
| 工作先告一段落，想休息8分钟 | 结束当前专注，明确开始8分钟休息 | 先去设置改以后所有休息的长度 |
| 暂时离开，下一步尚未决定 | 暂停或只结束，按用户所选执行 | 自动开始专注或休息 |

好用的判断包括：是否容易找到、能否看懂所改对象、是否保留已有过程、误触能否纠正、常用路径是否简短。不能只比较点击数。

## 2. 当前实现到底怎样

核对版本：[b132621](https://github.com/Hughstudy/clock/commit/b132621d8dc090600270a94f25531d972b6b0fd9)。本次只读取应用代码，没有修改或运行新的应用实现。

| 路径或限制 | 代码中的现状 | 对使用的影响 |
| --- | --- | --- |
| 开始前改专注时长 | 点时间数字／铅笔，选值并应用，再点开始 | 可临时改专注，选择与开始分开 |
| 专注已经开始 | 调时入口只在准备专注时可用；运行和暂停中均不能修改目标 | 继续原工作却想重新安排时间，没有直接路径 |
| 提前专注转休息 | 结束专注 → 确认结束 → 开始休息 | 操作区已展开、沿用休息长度时需3次点击 |
| 提前结束后再开专注 | 结束专注 → 确认结束 → 准备专注 → 开始专注 | 沿用时长也需4次；修改时长还需进入选择器 |
| 休息转专注 | 结束休息 → 开始专注 | 沿用时长需2次，目前没有休息结束确认 |
| 休息准备与专注结果 | 可选择短休息／长休息，读取各自设置值 | 没有和专注对等的单次分钟数选择界面 |
| 自然到期 | 结算当前一段，等待明确开始下一段 | 不会在用户离开期间自动累计多段 |

以上是代码路径计数，不是用户测试的耗时。未计入呼出已收起操作卡的一次点击，也未把输入、滑动或选择时间算作固定次数。

跨领域的借鉴：参数设置借鉴日历编辑的“选择值后仍在原处”；暂停和结束借鉴录音工具的两个不同动作；连续计时借鉴工时记录的“保留时间事实”。这些是设计类比，不是对所有日历或录音产品的实现描述，也不证明某一种方案必然最优。

资料能证明这些交互模式存在，不能证明它们已适合本产品，更不能用竞品营销文案推断对ADHD的效果。

## 5. 三种实质不同的方案

| 方案 | 核心变化 | 能解决什么 | 主要代价／反例 | 当前判断 |
| --- | --- | --- | --- | --- |
| A：合并结束与下一段准备 | 结束框里选下一段和分钟数，明确“结束并开始休息”；保留只结束 | 专注转休息少一步；下一段调时不用去设置 | 同一件事只是改剩余时间，仍被迫结束重开；框内分支更多 | 可做过渡，不足以作为本题主方案 |
| B：允许原段内重新安排时间 | 准备时选本次长度；运行／暂停时调整本段剩余时间；确实要换阶段时才结束并启动另一段 | 解决临时改时间，保留同一段记录、想法与伙伴活动；再补近处的切换入口 | 涉及计时、记录、并发和场景进度；不能当作只加一个按钮 | **优先做交互原型与规则验证，尚未批准实施** |
| C：连续记录，时间只是提醒 | 从开始到明确停止持续记投入，倒计时到点只提醒；专注／休息由用户明确切换 | 更适合不想被预设长度切断的长任务 | 离开应用未停止会多记；自然到期、完整章和休息建议规则均需重设计 | 保留为对照方案，本轮不建议推进 |

对A的最强反例：用户专注8分钟后只想再做10分钟，A仍制造两条专注记录。对B的最强反例：用户频繁加时，操作本身打断做事；如果把加时做成持续提示，反而鼓励反复管理计时。对C的最强反例：用户合上电脑离开，提醒结束后仍持续累计，记录失真。

因此，B应保留清楚的结束点和安静默认；不弹出“要不要再坚持”的加时劝导。先解决主动调整，再考虑快捷键或快捷加减，不一开始堆满常驻按钮。

## 6. 方案B的交互草案

### 6.1 同一个操作区，区分三种时间

| 所处状态 | 此时可修改的对象 | 暂定表达 | 提交的含义 |
| --- | --- | --- | --- |
| 准备专注／休息 | 本次将开始的长度 | 专注10分钟；休息8分钟 | 选值不开始，明确“开始专注／开始休息”才启动 |
| 专注／休息运行中 | 当前一段从确认时起还安排多久 | 已专注8分钟；从现在再计时10分钟 | 保留此前实际投入和原会话；应用后继续运行 |
| 专注／休息暂停中 | 恢复后还安排多久 | 已暂停；继续后再计时10分钟 | 应用只改剩余安排，仍保持暂停；继续由用户明确执行 |
| 设置 | 以后准备时使用的默认值 | 默认专注25分钟等 | 不更改正在运行或暂停的一段 |

调时与结束属于同一计时操作区，但不要求把全部内容同时塞在一个小确认框里。准备和调整时，当前模式、可改分钟数与提交动作在同一局部面板中；暂停／继续仍直接可达。安静运行保留清楚的倒计时。面板显示所编辑的值时，背景时间不再作为另一个可操作入口，避免两个“时间”争夺含义。

现有大时间与伙伴的关系先作为候选保留；本稿不预先锁定必须放在头顶或底部。小屏原型需要比较入口距离、遮挡和可达性后再决定。不能仅凭这张宽屏截图推导全部手机布局。

### 6.2 改时长的例子与边界

原定25分钟，已投入8分钟，还剩17分钟。用户选“从现在再计时10分钟”，应用后仍是同一段：已经投入的8分钟保留，之后再计10分钟。若最终完整跑完，实际投入合计18分钟；不额外增加一次参与，不迁移想法。

若编辑时又过去20秒，提交时已投入8分20秒，那么“从现在再计10分钟”应得到18分20秒的实际总量。界面可预览预计总计，但以明确的提交含义为准；不能悄悄把10解释成“本段总共10分钟”。存储保留秒和毫秒，不能为了显示整数分钟抹掉实际时间。

当前判断是优先编辑“剩余安排”，不是总时长；初始计划、当前安排和实际投入分别保存或可可靠推导，历史不伪装成用户一开始就选择了新长度。具体字段由实现设计确定，本稿不先写死数据库结构。

尚未通过的细节：

- 应用时重新核对原段身份和是否已到期；若早已结束，不恢复原段，提示已结束并另行开始。
- 0分钟不暗含“立即自然完成”。若用户要现在结束，使用明确的结束动作；非正值调时不提交。
- 初版不突破既有模式的总时长上限；“还可安排多少”须结合已投入时间计算，不把120分钟总上限悄悄改成每次还能加120分钟。
- 缩短后真正到期是否仍计一次到期、如何呈现原始计划，需随规则定稿；任何情况下，拖动或应用数值本身不得增加完成次数。
- 改本段不更改设置默认；是否记住下一次准备值应独立讨论，不能把不断缩短的剩余值变成下次默认长度。

### 6.3 真正换阶段时再使用组合操作

“改时间”留在原段；“去休息”明确结束原专注并开始另一段。转休息时，在同一面板显示下一段的分钟数，按钮写清“结束并开始休息”，同时提供“只结束”和取消。自然到期以后没有当前段需要确认结束，直接呈现下一段准备。

休息转专注也可研究明确的“结束休息并开始专注”，但必须让用户先看见将开始多久。不能将现有“结束休息”在保持名称不变的情况下改成自动开始。只结束休息的直接路径仍保留，不为了形式对称多加确认。

若一次操作包含结束与开始，业务上要校验同一目标、保护两步的一致性和重复提交；不能在按钮处理器里简单连发两个独立请求，任由第一步成功而第二步落在别的状态。保存失败要说明真实结果，不能显示已开始但计时实际未建立。

### 6.4 时间选择器先保持简单

沿用可见的“调整”入口、可读分钟数和现有可访问的输入能力。常见值可以按模式按需展开；运行中快捷加5分钟是否比自定义剩余值更好，需要原型验证。暂不增加长按、双击、隐藏滑动或把触摸伙伴作为调时入口。

进入选择器不自动暂停；取消不改变原安排；应用后回原位置，键盘焦点有明确落点。低屏高、大字号和软键盘下要能看见当前值与提交动作，不能只保证元素在页面里。

## 7. 二阶与三阶影响

| 直接改动 | 随后的影响 | 更远的影响与约束 |
| --- | --- | --- |
| 运行中调整剩余时间 | 到期点变化，旧通知／旧按钮可能失效 | 恢复、重试和其他标签页必须识别同一调整，避免旧到期覆盖新安排 |
| 同一段不再因调时而切开 | 想法归属与参与次数更连续 | 历史须区分原计划、调整后的安排和实际投入，不把一段改时算成多段完成 |
| 时长可增加 | 用“已投入／目标”算出的比例可能变小 | 伙伴动作不能倒演、物件不能撤回；以后故事进度也不能直接等于可变目标比例 |
| 时长可缩短 | 比例可能突然跳到故事末尾 | 不得补造没有发生的故事成果；计时到期与完整作者内容、保存成功仍分别核验 |
| 结束和开始合并 | 少一次点击，结果画面可能停留很短 | 仍保留当段记录与可回看入口，不强制看动画，也不因快速切换漏存 |
| 调时很容易 | 用户可能频繁操作而打断工作 | 默认保持安静，不不断建议加时；不把延长专注包装成更值得奖励 |
| 增加参数与分支 | 单个面板容易变高、状态组合增加 | 应按当前任务展示必要内容；测试以完整使用意图覆盖，不为每个控件复制一套规则 |

已发现的具体代码影响：`HomeScreen` 将 `totalMs` 与 `remainingMs` 交给角色；[useFocusPresence](../../src/hooks/companion/useFocusPresence.ts)在总时长变化时重新建立动作安排；[presentation](../../src/logic/presentation.ts)用记录时长比例表达进度；[storage](../../src/adapters/storage.ts)对未确认结束和磁盘上的时程进行比对。因此，“让数字可编辑”远不足以完成B。

场景处理的候选原则：已经发生的节点不可撤回，新安排只影响之后的节奏；若活动已完成，进入安静停留而不是重演。其连续进度、冷重开恢复和未来故事如何实现仍需专项验证，不在本研究中宣称已解决。

## 8. 站在反对者角度再审一次

**反对意见一：改时会破坏番茄钟的约束。** 本产品优先自主、真实记录与轻量开始，没有承诺严格训练固定25分钟。允许主动调整有理由；但不等于改为无限累加或自动劝加时。

**反对意见二：只有使用前选时间的入口不好找，没必要改计时模型。** 这个可能性仍成立。负责人的具体场景支持研究运行中重排，却不能证明它是所有用户的首要需要。对比原型必须包含A；若仅移动本次调时入口就能完成大部分任务，先做A更合理。

**反对意见三：统一面板比原来更复杂。** 若用户必须先从“调当前、调下一段、默认设置、切换模式、只结束”里选对象，统一就失败了。面板应由进入位置和当前状态确定对象，用户只处理眼前一件事。

**反对意见四：取消结束确认，用撤销更省事。** 当前没有可靠的会话结束撤销。撤销意味着恢复计时、原想法归属、场景位置及可能已经开始的新段，还要处理跨页保存。Session有这类能力，不代表本项目也能无成本获得。不能把暂时弹一个“撤销”提示当作已解决。

**反对意见五：既然能调时间，为什么不直接改为正计时。** 正计时更适合部分任务，但会改变用户对“多久可以停”的预期以及无人操作时的记录边界。它是C方案的产品选择，不应夹带在按钮整理中上线。

## 9. 后续验证：用任务证明，而非只看示意图

先制作A、B的可操作原型，C用流程稿检验价值即可。沿用同一场景与文案规模，避免把美术好看误当成流程好用。下表为待执行任务，不是已通过的测试。

| 任务 | 观察重点 |
| --- | --- |
| 首次打开，直接开始默认专注 | 常见开始路径是否仍一步可达 |
| 开始前改为10分钟；另一次只休息8分钟 | 不进设置也能完成；知道本次值与默认值的区别 |
| 已做8分钟，决定从确认时起再做10分钟 | 是否理解新剩余值；不结束重开；实际投入连续 |
| 暂停后改剩余时间，再离开面板 | 是否意外恢复计时；是否保留原段 |
| 专注转休息8分钟；休息提前转专注12分钟 | 能预测按钮会结束和开始什么；下一段长度可见 |
| 只想停止，不想安排下一段 | 能直接找到只结束，不被推入休息 |
| 输入过程中原段到期，或另一页已切换 | 旧提交不能延长已结束的段，也不能改到新段 |
| 连续调整、慢保存、失败重试、重开 | 数字不回跳、不丢点击、不重复增加记录；状态真实 |
| 伙伴动作进行到一半后加时／减时 | 不倒演、不重复开场、不补造完成成果 |
| 320／375／430宽度，200%文字及软键盘 | 值与主按钮可见、可达；目标不在按下后移位；焦点返回正确 |

可用性记录包括首次找到入口的耗时、走错路径、是否理解“总长／剩余”、实际操作次数及取消行为。原型自动化另核对会话身份、累计时间、草稿和场景状态。暂不捏造成功率或改善百分比。

从近期返工提炼的预防规则候选：先写清动作对象与结果；对每个新动作检查运行、暂停、到期、恢复和慢保存；共享样式删除先查所有消费者；交互测试验证最终用户意图而不是某个固定点击序列。若B获准，再将这些要求落实到相应验收和自动化，不为了写研究稿先增加框架。

## 10. 工程组织与下一次决策

给新接手者的概念应保持简单：准备值是未开始的安排，活动段保存真实计时，调时草稿在提交前没有业务作用，已结束结果是历史事实。避免用一个叫 `duration` 的值同时表示默认、原始计划、剩余和历史目标。

实现时应复用纯计时逻辑与统一保存入口。当前 `ready` 加 `result` 会同时表示初始准备、专注结果、休息结束后的准备；若增加活动调时，需要明确显示状态映射，避免继续叠加布尔条件。是否拆出小型计时控制组件，应按职责和复杂度决定，不为这次研究先重构整屏。

| 接下来需要确定的事 | 当前建议 | 成为实施规则前的证据 |
| --- | --- | --- |
| 先解决哪类困难 | 原段内重排剩余时间，优先B | 与A对比的任务原型 |
| 时间修改的含义 | 运行中是从提交时起还安排多久；暂停中是恢复后还安排多久 | 任务复述无歧义，边界计算一致 |
| 是否合并结束与下一段 | 可以，但独立保留只结束；不把调时变成结束 | 两个方向与只结束路径均清楚 |
| 调时后完成和故事怎么算 | 时间事实、到期和真实故事完成分别判断 | 更新计时／故事规则及失败恢复用例 |
| 改哪些现行文档 | 方案通过后同步A.1、UI、数据、动作和验收 | 同一次变更保持各模块一致 |

当前交付只有这份研究和文档地图入口。未更改“开始后目标锁定”等现行规则；未修改应用、数据格式或既有测试；未宣称竞品实机、用户研究或新交互验收已经完成。
